### 第 1 题的验证点：谁在转换类型？

你正确区分了字符串和整数；需要澄清“自动转换”的执行位置。

```python
raw = "80"
length = int(raw)  # 真正把 str 转成 int 的是你写的这一行
```

Settings 的 max_text_length: int 只是类型标注，不会替你转换。当前 Settings 是 dataclass，不是之前的 Pydantic 模型。实测 Settings(max_text_length="80") 仍保存字符串。类似 Java 的 Integer.parseInt(raw) 是主动转换；但 Python 的类型标注又不像 Java 编译期类型检查那样阻止你传入字符串。

### 第 2 题的验证点：环境属于哪个进程？

你对“未设置使用默认值，空字符串仍需校验”的解释正确。需要订正的是：本程序的 load_settings 在服务器进程中执行，读取的是服务器进程环境，不是调用 API 的客户端环境。

例如电脑 A 发 HTTP 请求给电脑 B 上的服务：B 运行 load_settings，就读取 B 的服务器进程环境。A 的环境变量不会随 HTTP 请求自动发给 B。因此无效配置是服务器配置问题，本题返回 503。

TestClient 的测试恰好在同一个进程里执行应用，所以 monkeypatch.setenv 可以影响 load_settings；这不表示真实 HTTP 能读取客户端系统变量。另一个终端改环境，也不会自动修改已经运行的服务进程环境。

### 第 3 题的验证点：配置是否真正用于 API 长度检查？

test_environment_scope_restores_default 只调用 load_settings，验证环境作用域恢复；它不向 API 发请求，因此不能发现路由仍写死 2000。

你自写的 test_custom_limit_rejects_before_analyzer_call 就能发现：设置上限 12，发送 13 个字符应当 413；如果实际限制仍是 2000，就会错误放行。test_configured_limit_allows_exact_boundary 也覆盖这类问题。

响应中的 max_length 必须与实际采用的上限一致；否则即使拒绝行为正确，客户端看到的限制仍是错的。

### 第 4 题的验证点：写出调用记录列表，并说明恢复条件

两次请求之后应为 [VALID_TEXT]，不是单独的 request.text 字符串：第一次 bad 配置在取得有效配置时失败，没有调用 analyze；第二次配置为 80 后成功，append 一次。

你对模块顶层缓存会导致继续使用旧值的说明正确。更精确地说：如果模块导入时缓存了 bad，后续即使修改同进程环境仍会使用缓存值；当前代码每次调用 load_settings 都重新读取，所以测试中的第二次请求能恢复。这不等于外部终端修改环境能热更新已经运行的服务。
